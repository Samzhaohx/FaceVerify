# 开发记录：问题定位与优化

本文档记录开发过程中实际遇到的问题、定位方式、根因与处理，以及量化后的优化效果。  
上游说明见 [README](../README.md)。

环境：Lenovo 笔记本，i7 移动端，无可用 CUDA，CPU 推理，输入 960×540。

---

## 一、算法链路

### 1. SCRFD 检不出人脸：anchor 数少了 64 倍

- **现象**：检测阶段抛 `ValueError: operands could not be broadcast together with shapes (0,) (800,)`。
- **定位**：打印 anchor 数量，640 输入、stride=8 时只有 200 个，正确值应为 `(640/8)² × 2 = 12800`。
- **根因**：`_anchors(height, width, stride)` 内部又做了一次 `height // stride`，而调用方传入的已经是特征图尺寸（`det_h // stride`），重复除使 80 变成 10。
- **处理**：函数内直接用 `np.mgrid[:height, :width]`，并在签名注释中标明"传入的是已除过 stride 的尺寸"。

### 2. 关键点形状不符，对齐断言失败

- **现象**：`AssertionError: 需要 5 点，实际 (10,)`。
- **根因**：SCRFD 的 kps 输出是 `(N, 10)` 扁平向量（5 点 × 2 坐标），代码直接取 `kpss[i]` 传给了对齐函数。
- **处理**：`kps=kpss[i].reshape(5, 2)`。

### 3. 192×192 对齐模板算错，对齐图被压扁 40%

- **现象**：106 个 2D 关键点画到脸上后完全散乱，部分落在头发和背景上。
- **定位**：把 5 点投影到对齐空间，眼距得到 37.3px，而模板要求 60.5px，缩放系数错了 0.617 倍，反投影自然把点推歪。
- **根因**：非 112 整数倍的尺寸用了"112 等比放大 + 补边"的错误公式。insightface 的约定是：非 112 倍数时以 128 为基准等比缩放，并右移 `8 × ratio`（8px 来自 96×112 与 112×112 模板的差值）。
- **处理**：
  ```python
  if image_size % 112 == 0:
      ratio, diff_x = image_size / 112.0, 0.0
  else:
      ratio, diff_x = image_size / 128.0, 8.0 * ratio
  dst = ARC_TEMPLATE_112 * ratio
  dst[:, 0] += diff_x
  ```
- **验证**：投影后 5 点与模板重合；106 点范围 x∈[624,1651]、y∈[1306,2404]，完整落在检测框 x∈[520,1772]、y∈[770,2452] 内。

### 4. 用 106 点重算 5 点做对齐，实测为负优化

- **背景**：设计上希望用 2D106 关键点提升对齐精度，直觉是点越多越准。
- **做法**：用 106 点中的瞳孔/鼻尖/嘴角重算 5 点再对齐。索引通过数据驱动反推（在 192 对齐空间里找离模板落点最近的 106 点下标，5 张照片投票）。
- **结果**（同一人 5 张照片两两余弦相似度）：
  | 5 点来源            | min       | mean      | max   |
  | ---------------- | --------- | --------- | ----- |
  | SCRFD 原生 5 点     | **0.546** | **0.654** | 0.750 |
  | 106 点重映射（投票最优索引） | 0.504     | 0.623     | 0.782 |
  | 106 点重映射（初版索引）   | 0.401     | 0.573     | 0.752 |
- **根因**：SCRFD 的 5 点是端到端为"对齐"回归训练的，位置精度即训练目标；2D106 是在**已对齐**的 192 裁剪图上预测 106 点，输出自带对齐残差，反投影回原图会叠加误差。此外 106 点索引语义在不同导出模型间不统一（投票在眼部区域不一致）。
- **处理**：ArcFace 对齐仍使用 SCRFD 5 点；106 点改用于两件它确实更优的事：活体输入裁剪（更贴脸，减少背景干扰）与对齐质量可视化。`landmark.refine()` 只补 `kps106`，不覆盖 `kps`。

### 5. 活体多尺度集成把真人判成攻击

- **现象**：初版默认 `scales=(2.7, 4.0)` 多视图平均，某张真人自拍 live=0.581，落入"活体异常"。
- **定位**：逐尺度扫描 5 张真人照片，分数随尺度单调劣化：
  | 裁剪尺度                | 5 张真人 live                                    | 稳定性  |
  | ------------------- | --------------------------------------------- | ---- |
  | 2.0 / 2.4 / **2.7** | 全部 1.000                                      | 极稳   |
  | 3.2                 | 0.999 / 0.999 / 0.899 / 0.991 / 0.996         | 开始抖动 |
  | 4.0                 | 0.936 / 0.985 / **0.191** / 0.859 / 0.975     | 明显抖动 |
  | 4.6                 | **0.209** / 0.816 / **0.004** / 0.670 / 0.829 | 失效   |
- **根因**：MiniFASNet 在固定裁剪协议（人脸框外扩 2.7 倍）下训练。4.0 倍时画面混入过多头发、背景、镜片反光，已偏离训练分布；分布外输入的概率没有物理意义，平均进来只会污染结果。
- **处理**：默认改为单尺度 `scales=(2.7,)` + 水平翻转（2 视图平均，仅降噪）。多尺度代码保留但默认关闭，并在注释标注"4.0 为分布外"。
- **效果**：真人 5/5 稳定 1.000、方差 0；单帧活体耗时 5ms → 2.6ms。

### 6. 裁剪框内出现黑边，真人被判成照片

- **现象**：自测序列 60 帧全部"活体异常"，分数 0.03；同一张照片在原图上跑为 1.000。
- **定位**：
  1. 先验证是否与尺寸相关——把人脸从 1251px 缩到 120px 逐档测试，**全部 1.000**，排除尺寸因素；
  2. 保存裁剪图查看，发现竖构图素材被 letterbox 到横屏，人脸左右各有纯黑边，占裁剪图约 16%；
  3. 仅将填充方式从黑色改为边界复制，分数立即回到 **1.000**。
- **根因**：MiniFASNet 的负样本中大量存在"照片/打印件置于屏幕"的样本，纯黑矩形边界是强攻击特征。裁剪时补黑边等于给真人加上"屏幕边框"。模型本身更关注结构/材质而非画质细节（见第 15 条）。
- **处理**：`_crop()` 不再补边，改为把裁剪框中心拉回画面内、必要时缩小边长，保证裁剪 100% 落在图像像素上：
  ```python
  side = min(side, min(w, h))
  cx = min(max(cx, half), w - half)
  cy = min(max(cy, half), h - half)
  ```
- **附带修复**：自测脚本的模拟画面也从黑色填充改为 `BORDER_REPLICATE`，避免测试本身制造假阴性。

## 二、工程链路

### 7. `np.vstack` 导致检测崩溃，仅特定场景复现

- **现象**：单张高清图正常，换成视频流后偶发 `ValueError: all the input array dimensions except for the concatenation axis must match exactly`。
- **根因**：各 stride 命中数不同，`scores_list` 中为长度不等的 **1-D** 数组；`np.vstack` 把 1-D 数组当行堆叠，长度不一致即报错。高清图下三个 stride 恰好各命中 1 个，长度一致，问题被掩盖。
- **处理**：`scores` 用 `np.concatenate`，`bboxes`/`kpss` 用 `np.concatenate(axis=0)`。

### 8. 安装了 onnxruntime-gpu 但用不上 GPU，且日志污染

- **现象**：启动时 stderr 输出 `Error loading "...onnxruntime_providers_cuda.dll" which depends on "cublasLt64_13.dll" which is missing`，随后降级 CPU。功能正常，但每个模型需承担一次约 0.3s 的失败建会话耗时（4 个模型约 1.2s）。
- **根因**：`onnxruntime-gpu` 仅为 Python 包，CUDA/cuDNN 运行时 DLL 需单独安装并加入 PATH；`get_available_providers()` 只反映该 ORT 是否为 GPU 版，不代表运行时可用。
- **处理**：增加廉价预检——用 `ctypes.CDLL` 尝试加载 `cublasLt64_13/12/11.dll`（Linux 对应 `libcublasLt.so.*`），失败则直接走 CPU 并输出明确提示；保留 `try/except` 兜底处理显存/驱动类运行时错误；支持 `ORT_DEVICE=cpu` 强制 CPU。
- **效果**：启动日志从二十余行报错收敛为一行说明；启动加快约 1.2s；Web 面板「设备」标签直接显示当前后端。

### 9. MJPEG 推流不能直接调用 `cap.read()`

- **问题**：在 Flask 的 `Response(generator)` 中调用 `read()`，导致 ① `read()` 阻塞 33ms 拖慢推理；② 每个浏览器连接各开一个生成器，互相抢占摄像头；③ 网络慢时帧积压，延迟持续增大。
- **处理**：
  - 采集独立线程 + 有界队列（`FRAME_QUEUE_SIZE=2`），队列满时丢弃最旧帧；
  - 推理线程从队列取帧处理，Flask 只读取"最新一张 JPEG"，不直接访问摄像头；
  - `dropped` 计数暴露到面板。
- **效果**：多设备同时预览互不干扰；推理慢只影响帧率，不影响延迟。

### 10. Windows 摄像头打开慢、720p 帧率低

- **处理**：
  - 后端按优先级尝试 `CAP_DSHOW → CAP_MSMF → 默认`（macOS `AVFOUNDATION`，Linux `V4L2`）；
  - 设置 `CAP_PROP_FOURCC='MJPG'`：UVC 摄像头在 720p/1080p 下若走 YUY2，会受 USB 带宽限制掉到 5~10fps；
  - `CAP_PROP_BUFFERSIZE=1`，避免 `read()` 拿到数帧之前的画面；
  - 连续 30 次读帧失败自动重开设备；
  - 启动 3 秒后自检采集帧率：<2fps 重开一次，明显低于请求值时输出可操作提示。
- **实测**（同一台机器，三次协商结果不同）：
  | 采集分辨率    | 实际帧率 |
  | -------- | ---- |
  | 1280×720 | 15.4 |
  | 960×540  | 26.3 |
  | 640×480  | 30.3 |
  因此默认分辨率定为 960×540。

### 11. 中文标注显示为乱码

- **根因**：`cv2.putText` 使用 Hershey 矢量字体，不含 CJK 字形。
- **处理**：PIL + 系统字体（Windows `msyh.ttc`，macOS `PingFang.ttc`，Linux `NotoSansCJK`），自动探测，`FONT_PATH` 可覆盖。
- **性能**：采用"整帧 BGR→RGB 一次 → 所有框与文字绘制完 → 转回 BGR"，整帧标注 2.7~4.5ms；若按每段文字单独转换会超过 20ms。

### 12. 相似度在阈值附近抖动，同一人反复通过/不通过

- **现象**：自测 60 帧内相似度在 0.32~0.91 波动，7% 的帧低于阈值，状态在"验证通过/身份不匹配"间闪烁。
- **根因**：单帧特征受运动模糊、压缩噪声、关键点抖动影响；检测帧与预测帧的关键点质量也不同。
- **处理**：同一轨迹内对特征向量做 EMA 融合后再比对：
  ```python
  fused = (1 - w) * prev_emb + w * emb
  fused /= np.linalg.norm(fused)
  ```
- **实测**：
  | `EMBEDDING_SMOOTH` | mean  | min   | std   | 低于阈值比例 |
  | ------------------ | ----- | ----- | ----- | ------ |
  | 1.0（关闭）            | 0.865 | 0.317 | 0.178 | 7%     |
  | **0.5（默认）**        | 0.909 | 0.746 | 0.063 | 0%     |
  | 0.3                | 0.913 | 0.862 | 0.034 | 0%     |
- **权衡**：0.3 更稳定但身份切换响应更慢；0.5 为平衡点。

### 13. HEIC 素材、中文路径与 EXIF 方向

- `cv2.imread` 不支持 HEIC → 用 `pillow-heif` 注册 opener 后由 PIL 读取。
- `cv2.imread` 在 Windows 下遇到中文路径返回 `None`（内部使用 `fopen`，不识别 UTF-8）→ 统一走 `np.fromfile` + `cv2.imdecode`。
- 手机照片带 EXIF 方向标记，直接读会躺倒 → `ImageOps.exif_transpose()`。
- 三处问题统一收敛在 `register.py` 的 `imread_any()` 中。

### 14. Flask 调试重载导致摄像头被打开两次

- **现象**：`debug=True` 时第二个进程报"无法打开摄像头"。
- **根因**：reloader 会 fork 子进程，父子进程都执行了引擎初始化。
- **处理**：`app.run(..., use_reloader=False)`；引擎改为懒加载单例 + 线程锁，任何入口都只初始化一次。

## 三、可观测性

### 15. "活体 0.30 < 0.65" 无法指导排查

- **背景**：初版只输出状态与分数，用户无法区分"确实是攻击"与"画面问题导致的误判"，而后者在实际使用中占多数。
- **第一版方案（废弃）**：用"裁剪框是否越界"判断黑边。结果 5 张真人照片**全部**被判"贴边"——活体需外扩 2.7 倍，大脸几乎必然越界，该指标无区分度。
- **第二版方案**：在送入模型的 80×80 patch 上计算三个客观指标：
  | 指标           | 定义                                         |
  | ------------ | ------------------------------------------ |
  | `brightness` | 灰度均值                                       |
  | `sharpness`  | Laplacian 方差                               |
  | `dark_edge`  | 外圈（去掉内圈）灰度 < 32 的像素占比，用于发现 letterbox/播放器边框 |
  实测标定：
  | 场景           | live      | 亮度      | 清晰度       | 黑边占比          |
  | ------------ | --------- | ------- | --------- | ------------- |
  | 真人 5 张       | 1.000     | 102~138 | 3219~8479 | **0.07~0.24** |
  | letterbox 黑边 | **0.007** | 109     | 6680      | **0.56**      |
  | 压暗到 22%      | 1.000     | 29      | 434       | 0.42          |
  | 高斯模糊 σ=12    | 1.000     | 136     | 2975      | 0.17          |
  | 缩小到人脸 70px   | 1.000     | 136     | 2567      | 0.17          |
  | 过曝           | 0.885     | 229     | 7593      | 0.00          |
  | 合成摩尔纹翻拍      | 0.175     | 145     | 6115      | 0.18          |
- **两个结论**：
  1. MiniFASNetV2 对压暗、模糊、小脸不敏感（这些场景仍为 1.000），真正敏感的是边框/材质等结构特征。因此这些指标**只用于判定失败后解释原因**，不可作为判假依据，否则会形成"越黑越像攻击"的错误逻辑。
  2. 黑边告警需前置条件"人脸曝光正常"（亮度 ≥ 55），否则整体偏暗的房间会被误报（压暗场景黑边占比 0.42，但那只是暗，不是边框）。
- **文案排序**：先给具体可操作原因（黑边/偏小/偏暗/过曝/模糊），再给分数结论。
- **排版**：原因行最长 30 余字，最初按其他行宽度截断；改为允许底板为该行单独加宽（上限 460px × 缩放），并将文案收敛至 20 字以内。

### 16. 镜像预览应放在渲染层而非数据层

- **需求**：预览呈自拍效果。直觉做法是在 `cap.read()` 后立刻 `cv2.flip(frame, 1)`，整条链路跑镜像帧，坐标天然一致。
- **问题 1**：ArcFace 并非严格翻转不变。同一张脸原图与镜像图的 512 维特征余弦、以及各自与库内样本的匹配分：
  | 照片    | 特征余弦  | 原图匹配分 | 镜像匹配分 |
  | ----- | ----- | ----- | ----- |
  | photo 1 | 0.943 | 1.000 | 0.943 |
  | photo 2 | 0.911 | 1.000 | 0.911 |
  | photo 3 | 0.949 | 1.000 | 0.949 |
  | photo 4 | 0.920 | 1.000 | 0.920 |
  | photo 5 | 0.909 | 1.000 | 0.909 |
- **问题 2**：翻转后再绘制中文，文字呈镜像反向。
- **处理**：分析链路一律运行于原图；输出前才翻转像素，并将人脸框 x 坐标镜像映射（`x' = w-1-x`），文字最后绘制。
- **验证**：同一序列 `MIRROR=True/False` 两次运行，相似度均为 0.958、活体均为 0.998；框坐标 550.1→429.9、849.1→728.9，满足 `x' = 1279 - x`。额外成本为一次 `cv2.flip`（960×540 约 0.2ms）。

## 四、性能优化手段汇总

| 手段                        | 效果                    | 代价                |
| ------------------------- | --------------------- | ----------------- |
| 跳帧检测（`DETECT_INTERVAL=2`） | 检测耗时摊薄 50%            | 快速移动时框略有滞后（卡尔曼补偿） |
| 识别结果按 track 缓存（15 帧）      | ArcFace 调用降低约 93%     | 身份更新延迟约 0.5s      |
| 特征 EMA                    | 相似度 std 0.178 → 0.063 | 换人响应变慢（新轨迹会重置缓存）  |
| 活体单尺度                     | 耗时 5ms → 2.6ms，且更准    | 无                 |
| 采集/推理解耦 + 丢旧帧             | 延迟恒定                  | 丢帧（可观测）           |
| 整帧一次 PIL 转换               | 标注 4ms 级              | 无                 |
| ORT 线程限制（4/2）             | 多模型串行吞吐更稳             | 单模型峰值略降           |

**结论**：推理耗时 11~~27ms（约 35~~90 FPS）；端到端帧率上限由摄像头协商到的采集帧率决定。
